# Lab 3: Exception and Interrupt
This project implements a comprehensive exception and interrupt handling system for the Raspberry Pi 3. It covers switching between exception levels, handling synchronous exceptions and hardware interrupts, implementing asynchronous I/O, and managing concurrent tasks with a preemptive, priority-based scheduler.

### Project Structure
The project has been refactored into a more modular structure:
* `boot/`: Contains bootloader and kernel startup assembly code and linker scripts.
* `src/`: Contains all C source code, separated into kernel, bootloader, and lib.
* `include/`: Contains all header files.
* `user/`: Contains the source code and Makefile for building test user programs.

## Basic Exercise 1: Exception
**Goal:** The primary goal is to understand and manage Armv8-A's exception levels, enabling the kernel to run a user program in an unprivileged mode (EL0) and handle synchronous exceptions (like system calls) generated by it.

**Implementation Details:**
* **EL2 to EL1 Switch:** At boot, the kernel immediately switches from the default EL2 to EL1. This is done in boot/kernel/boot_kernel.S by configuring hcr_el2 and using eret to jump to the C kernel entry point in EL1.
* **EL1 to EL0 Switch:** A run command is added to the shell, which executes a user program from the initramfs archive.
The run_userprogram.c file handles finding the program in the CPIO archive, loading it into memory, and setting up a stack for the user space.
It then calls switch_to_el0, which sets spsr_el1 to unmask interrupts for EL0, sets elr_el1 to the program's start address, points sp_el0 to the user stack, and executes eret to drop to EL0.
* **Exception Vector Table:** The vector table base address register (vbar_el1) is set to point to exception_vector_table defined in boot/kernel/exception.S. This table has 16 entries, each branching to a specific handler based on the exception type and origin EL.
* **Synchronous Exception Handling:** The test user program (user/userProcessStatus.S) uses the svc instruction to trigger a synchronous exception.
This exception is caught by the sync_lower_el_64_handler in the vector table.
The C handler sync_lower_el_64_entry in src/kernel/exception_entry.c is then called, which prints the contents of spsr_el1, elr_el1, and esr_el1 to show the cause of the exception.
* **Context Saving:** To prevent the handler from corrupting the user program's state, the save_all and load_all macros in exception.S are used. They save and restore all 31 general-purpose registers (x0-x30) as well as spsr_el1 and elr_el1 on the kernel stack upon entering and exiting an exception.

## Basic Exercise 2: Core Timer Interrupt
**Goal:** This exercise focuses on enabling and handling a basic hardware interrupt from the CPU core's built-in timer.

**Implementation Details:**
* **Timer Configuration:** Before jumping to a user program in EL0, the el0_core_timer_enable function is called. This function:
Enables the timer by setting cntp_ctl_el0 to 1.
Sets an initial expiration time using cntp_tval_el0.
Unmasks the timer interrupt from the first-level interrupt controller by writing to the CORE0_TIMER_IRQ_CTRL address.
* **Interrupt Handling:**
The IRQ from EL0 is routed through the vector table to lower_el_irq_exception_handler.
This handler calls lower_el_irq_entry, which checks if the interrupt is from the core timer by reading CORE0_INTERRUPT_SOURCE.
Upon a timer interrupt, it enqueues a task to print the elapsed time (calculated using cntpct_el0 and cntfrq_el0) and then resets the timer to fire again in 2 seconds.

## Basic Exercise 3: Rpi3's Peripheral Interrupt
**Goal:** The goal is to replace the inefficient busy-polling UART driver with an interrupt-driven, asynchronous I/O system.

**Implementation Details:**
* **Asynchronous Buffers:** Two circular buffers, tx_buffer and tx_buffer, are implemented in src/lib/uart.c to hold outgoing and incoming data.
* **Interrupt Enable:** UART interrupts are enabled by setting the correct bits in both the Mini UART's Interrupt Enable Register (AUX_MU_IER_REG) and the second-level interrupt controller's ENABLE_IRQS1 register. This is managed by functions in src/kernel/gpu_interrupt.c.
* **Interrupt Source Determination:** The main IRQ handler, el1_irq_entry, first checks if the interrupt is from the GPU/peripherals and then if it is specifically a UART interrupt by checking the corresponding pending registers.
* **Asynchronous Read/Write:**
uart_async_send_string adds characters to the tx_buffer and enables the TX interrupt. The actual sending is performed by a task (process_uart_tx_data) triggered by the interrupt handler when the UART hardware is ready to transmit more data.
The RX interrupt handler reads all available data from the UART hardware and enqueues a task (process_uart_rx_data) to place the data into the rx_buffer. Shell functions can then read from this buffer without blocking.

## Advanced Exercise 1: Timer Multiplexing
**Goal:** Implement a timer API that allows multiple, one-shot timeout events to be scheduled using only the single physical core timer.

**Implementation Details:**
* **Timer Queue:** A sorted linked list (timer_queue) is implemented in src/kernel/timeout.c. It stores timer_t objects, each containing a callback function, user data, and an absolute expiration time.
* **add_timer API:** The add_timer(callback, data, duration) function provides the core API. It creates a new timer event, inserts it into the queue in sorted order, and if the new timer is now the soonest to expire, it reprograms the hardware core timer.
* **setTimeout Command:** A non-blocking setTimeout MESSAGE SECONDS command is added to the shell for testing. It uses add_timer to schedule a message to be printed in the future.
* **Interrupt and Task Handling:** The core timer interrupt handler is lightweight. It simply enqueues a high-priority task (process_timer_tasks) to do the actual work. This task checks the timer queue, executes the callbacks for all expired timers, and reprograms the hardware timer for the next scheduled event.

## Advanced Exercise 2: Concurrent I/O and Preemption
**Goal:** To build a simple, priority-based, preemptive multitasking system for handling deferred tasks, allowing long-running I/O processes to be handled without blocking more critical interrupts.

**Implementation Details:**
* **Task Queue:** A global task queue is implemented in src/kernel/task_queue.c. Interrupt handlers are decoupled from heavy processing; they perform minimal work and enqueue a task for later execution.
* **Preemptive Priority Scheduling:** The scheduler implements preemption. The get_highest_priority_task function always scans the entire queue and returns the task with the highest numerical priority, regardless of when it was added. This ensures that if a high-priority task (e.g., from the timer) is enqueued, it will be executed before any lower-priority tasks already in the queue.
* **Nested Interrupts:** The system supports nested interrupts.
Before processing the task queue, the kernel re-enables interrupts. This allows a higher-priority interrupt (like a timer event) to preempt the execution of a lower-priority task (like UART processing).
To support this, the save_all macro was extended to also save and restore spsr_el1 and elr_el1, preserving the context of the interrupted handler.
* **Task Execution:** After any interrupt, and before returning to the previous context, the process_task_queue function is called to run any pending tasks. This ensures that deferred work is completed as soon as possible.
